User:有没有人针对项目优化开发了skill用于优化特定部分的数据结构。或者说根本就不需要ai自己就能判断
LLM(deepseek v4.1 flash 1017):
有，而且不少——但真正有信息量的那一类，和你想的“数据结构优化 skill”可能不是同一个东西。

搜索里能看到三种典型产物：

- **教科书型**：比如 `data-structure-optimizer`（把 `Array → HashMap`、`O(n²) → O(n log n)` 写成一份 SKILL.md）。这类东西的边际价值接近零，因为这些知识本来就在模型权重里。
- **方法论型**：比如 `extreme-software-optimization`（profile first → 一次只改一处 → golden output 做等价性证明 → 收益门槛打分）。它有价值，但价值在“约束 AI 别乱来”，不在“教它数据结构”。
- **项目绑定型**：比如 Adobe 官方那份 `performance` skill。它开篇就是“这条只在 `@adobe/data` 的 V8 热点派发循环里成立”，配了隐藏类单态化的因果解释、`%HaveSameMap` 校验、以及“focused bench ≥25% 且 full perftest ≥10% 才保留，否则回滚”的硬门槛，还专门写了 *When not to apply*。这类东西模型**绝对猜不出来**，这才是 skill 的真正形态。

## 所以“AI 自己能不能判断”，要拆成三件事

关键在于：**“该用什么数据结构”和“这里该不该动”是两个完全不同难度的判断**。前者是公开知识，后者依赖模型看不到的上下文——真实数据规模与访问分布、延迟/内存预算、持久化格式的向后兼容、并发模型、GC 压力、以及谁在调用这个内部结构。

这也是为什么那份 Adobe skill 的作者反复强调“三个条件必须同时满足”——那三个条件没有一条能从代码里读出来。
## 真正该分给三个角色的部分

| 环节 | 谁来做 | 为什么不能互换 |
|---|---|---|
| **测量**（哪里慢、慢多少、内存峰值） | profiler / benchmark / CI，确定性工具 | 让模型“目测复杂度”是最常见的翻车点，它会把不热的代码优化得很好看 |
| **判断**（候选结构、重构方案、落笔） | AI | 模式识别和批量改写本来就是它的强项 |
| **裁决**（值不值得动、能不能破兼容） | 人 | 涉及预算和外部契约，AI 没有权限也没有信息 |

有个说法很到位：*never send an LLM to do a linter's job*。同理，别让 AI 去做 profiler 的活。确定性的事交给确定性工具，这也是为什么那几份成熟 skill 的第一条都是 “profile first”，而不是“分析一下复杂度”。

## 至于要不要写，判据其实很清楚

按 Anthropic 自己的分层逻辑：**规则错两次就进 CLAUDE.md／AGENTS.md，第三次还在重复解释才升级成 skill，必须每次无例外生效的写成 hook**。而且有实测数据支持——Vercel 把 8KB 文档索引放进 AGENTS.md 拿到 100% 通过率，同一份内容做成 skill 只有 53%，因为 56% 的情况下 agent 压根没调用它。反过来，强行塞进去的公共 skill 会让通过率下降 1.3%–4.2%、token 成本涨 72%–394%。

所以对“数据结构优化”这件事，我的判断是：

- 通用版 skill：**别写**，收益为负，会挤占上下文还会稀释真正重要的规则。
- 项目版 skill：**有明确收益**，但它的内容应该长这样——不是“怎么优化”，而是“这里优化过、这是当时的数据、这是不能碰的边界、这是验收线”。

```
项目名-数据结构约束/
├── SKILL.md          # 触发条件 + 热点清单 + 禁用改造 + 验收门槛
└── references/
    ├── hot-paths.md  # 真实调用频次与 QPS、数据规模量级
    ├── invariants.md # 顺序性/去重语义/序列化兼容 等不可破的契约
    └── budget.md     # 延迟、内存、GC 指标的上限与测量命令
```

其中 `invariants.md` 是最关键的一份——**绝大多数“优化”事故不是选错了结构，而是悄悄改掉了语义**（把 list 换成 set 丢了顺序，把 map 换成有序结构改变了迭代结果，改了持久化格式导致老数据读不出）。这部分恰恰是 AI 永远猜不到的。
